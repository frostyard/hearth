# Plan: Roadmap

This plan delivers hearth: the Protobuf options, the `protoc` plugins and the
Go runtime that give a first-party app its API, its MCP tools, its permission
checks, its events and its versioned manifest
(frostyard/core
[ADR-0085](https://github.com/frostyard/core/blob/main/docs/adr/0085-build-new-first-party-apps-on-hearth-with-lodge-as-their-hub.md)).
It builds the toolkit, not an app: the first app is `frostyard/frostmarks`,
which has its own plan.

hearth is an incubating repository of frostyard/core
[Plan 0002](https://github.com/frostyard/core/blob/main/docs/plans/0002-org-portfolio-roadmap.md#incubating-repositories).
Its exit criteria are the pilot of ADR-0085's plan: an app built on hearth,
served by lodge, with 1 agent grant, and its manifest gate in `make ci`. The
decision date is 2027-03-31: on that date the organization keeps the repository
as a product, or retires the work.

## Phase 1 — Options, model, manifest and the gate (built 2026-11-15)

- The repository baseline of frostyard/core ADR-0071, with a Go gate
  ([ADR-0005](../adr/0005-run-the-repository-gate-in-go.md)) and the docs site.
- The 3 options, and the shared model with every rule of
  [specs/options.md](../specs/options.md)
  ([ADR-0004](../adr/0004-generate-the-manifest-from-protobuf-options.md)).
- The manifest format, its schema, its canonical JSON, its diff and the CLI
  ([specs/manifest.md](../specs/manifest.md)).
- The end-to-end demo app of `testdata/e2e/`, whose manifest is committed and
  regenerated by `make gen-check`.
- **Done when:** `make ci` passes; `hearth manifest diff` exits 1 on a breaking
  change of an app at the same version and 0 on its next major version; and the
  plugin refuses an RPC without `hearth_rpc`, permission, effect or exposure.

## Phase 2 — The permission runtime, the lodge adapter and MCP (built 2026-11-15)

- `cmd/protoc-gen-hearth-authz` and `authz/`: the per-RPC permission check from
  the model, a grant as a list of items (a capability on a path), and the
  generated hook that resolves a stored object's selector inside a
  transaction ([ADR-0006](../adr/0006-check-permissions-in-the-app-and-trust-lodge-only-on-its-socket.md),
  [specs/permissions.md](../specs/permissions.md)).
- `lodge/`: the adapter that reads `Lodge-Principal` and `Lodge-Grant` only on
  the app's lodge socket, after the peer check.
- `cmd/protoc-gen-hearth-mcp` and `mcpserver/`, with the tool schema from the
  proto3 JSON mapping and the effect as the tool's hints
  ([ADR-0007](../adr/0007-generate-mcp-tools-from-agent-rpcs.md),
  [specs/mcp-tools.md](../specs/mcp-tools.md)).
- The stdio MCP server of an app (`<app>ctl mcp`), which needs no token and
  acts as the local user.
- The demo app of `internal/e2e/`, which implements the generated hooks for an
  in-memory store and serves its generated tools over stdio.
- **Done when:** 1 demo app on an in-memory grant refuses a call that the grant
  does not cover, names the missing capability and selector, and serves its
  tools to an MCP client over stdio with no token. Both hold in
  `internal/e2e`, whose tests also prove that an app without a hook does not
  build.
- The Connect wiring of an app's tools moved to phase 4: the generated tools
  take a Go interface, and the client that satisfies it arrived with the
  `Connect` route.

## Phase 3 — Events, transports and the example app (built 2026-11-16)

- `cmd/protoc-gen-hearth-events` and `events/`: the CloudEvents envelope, the
  topic with its path segments, the read filters of a grant, and 1 publisher
  for each event message
  ([ADR-0008](../adr/0008-publish-thin-events-through-a-transactional-outbox.md),
  [specs/events.md](../specs/events.md)).
- `events/outbox`: the outbox table written in the change's transaction, and
  the relay that publishes each event with its id as `Nats-Msg-Id` and deletes
  it after the acknowledgement.
- The transports: `events/inproc`, the standalone bus that reads the same
  outbox, and `events/broker`, which publishes over a Unix socket to a NATS
  server with JetStream, such as lodge's broker socket.
- `examples/notes-lite`, a module of its own built from its README alone, with
  its own gate and the manifest diff in it
  ([ADR-0009](../adr/0009-keep-the-example-app-a-module-of-its-own-built-from-its-readme.md)).
- A README for a developer outside frostyard: the options, the plugins, and the
  standalone and lodge modes.
- **Done when:** the relay loses no event when it stops after the commit or
  after the publish, and the broker stores 1 message after a repeat; a
  subscriber with a read filter receives the events of its path and not the
  others; and `make ci` builds and tests the example from a clean checkout.

## Phase 4 — The Connect route (built 2026-11-16)

- `connectserver/`: the API of an app's service over Connect, served on the
  app's private socket as the local user and on its lodge socket under
  `/connect/` with lodge's caller, with the interceptor that maps the permission
  runtime's refusals to Connect's codes and text
  ([ADR-0010](../adr/0010-serve-the-connect-route-with-a-go-mod-pinned-generator.md),
  [specs/connect.md](../specs/connect.md)).
- A pin for `protoc-gen-connect-go` that meets the tool invariants: a `tool`
  directive of `go.mod`, whose checksum is in `go.sum`, and a `go run` plugin in
  each buf template, which `internal/workflowcheck` guards. The `simple` option
  makes the authz API the handler and the generated client the agent API.
- The demo app of `internal/e2e` and the example app serve their API over
  Connect on both sockets, and their tests prove the refusal's code and text.
- **Done when:** the example app serves its API over `Connect` on both sockets,
  and a refused check returns `permission_denied` with the permission runtime's
  text.

## Later / ideas

- A `hearth init` that writes an app's first service and its `make ci`.
- The `connect-es` TypeScript client generated beside the Go client.
- The deferred extension numbers: move from the in-house range when the
  Protobuf global extension registry grants a number.

## Open questions

None: phase 4 answered the question of who writes an app's `Connect` route.
`protoc-gen-connect-go` writes it, the app serves it on its own 2 sockets behind
`connectserver/`, and lodge forwards a user's call at `/connect/<service>/<method>`
([ADR-0010](../adr/0010-serve-the-connect-route-with-a-go-mod-pinned-generator.md)).
